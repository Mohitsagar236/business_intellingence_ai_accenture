§1

Introduction & Goals

This document translates the SRS into a concrete system design. Four design goals drive every decision below:

  • Correctness — a cause is never asserted without converging structured and unstructured evidence.
  • Trust — every claim in a report is traceable back to the evidence that produced it.
  • Speed — an incident goes from raw signal to routed report in minutes.
  • Extensibility — new data sources and playbooks can be added without touching the core pipeline.
§2

Architecture Overview

The system is a four-stage, event-driven pipeline. Each stage is an independently deployable service that consumes an event, does one job, and either emits the next event or halts the pipeline with a reason. A central metadata store records every decision — including suppressed and ambiguous cases — so the full evidence trail behind any report, or any silence, can be audited.

Stage 1

Data Ingestion

Structured connectors (CRM, ERP, ticketing, finance, HR) + unstructured connectors (notes, tickets, surveys, reports) write into a unified Observation Store.

Stage 2

Noise Filtering

Data-quality checks, STL decomposition, and sample-size-scaled significance testing separate real anomalies from normal variation.

Stage 3

Root-Cause Engine

Segments the anomaly, mines structured and unstructured evidence in parallel, and requires both to converge before naming a cause.

Stage 4

Recommendation

Matches the cause to a playbook, generates a grounded narrative, and routes the finished report to the owning department.

§3

Component Design

3.1Data Ingestion Layer

Realizes FR-1.1 – FR-1.4

Ingestion Layer

  • Structured connectors pull from CRM, ERP, ticketing, finance, and HR — via API where available, else a change-data-capture replica so the source system is never queried live.
  • Unstructured connectors pull call notes, emails, ticket text, surveys, and reports into a document store, then chunk and embed them.
  • Entity & time alignment resolves each record to a canonical account / region / product entity and a normalized timestamp.
  • Output: a unified Observation Store — a structured metrics table plus an indexed unstructured evidence store.

3.2Noise Filtering Engine

Realizes FR-2.1 – FR-2.5

Noise Filtering Engine

  • Data-quality module — schema/sync validation, duplicate detection, and definition-change detection via schema diffing against the last known-good state.
  • STL decomposition module — per-KPI trend / seasonal / residual decomposition.
  • Significance-check module — a sample-size-scaled confidence interval test on the residual.
Gate

Below threshold → logged to the Suppressed-Report Store, pipeline halts. Above threshold → a Confirmed Anomaly event is emitted to Stage 3.

3.3Root-Cause Engine

Realizes FR-3.1 – FR-3.6

Root-Cause Engine

  • Segmentation module — slices the anomaly along region / product / account / channel, ranked by contribution to the deviation.
  • Structured correlator — searches the Observation Store for other metrics co-moving within the anomaly's time window.
  • Unstructured theme miner — NLP clustering over the evidence index, scoped to the same window and segment, extracting dominant themes with excerpt citations.
  • Convergence check — a cause is only validated if a structured signal and an unstructured theme align in timing and direction.
Gate

Converges → cause passes to Stage 4 as Validated Cause. Does not converge → Ambiguous Case Handler ranks surviving hypotheses and computes the specific missing evidence — the "disambiguation gap" — that would resolve each.

3.4Recommendation Engine

Realizes FR-4.1 – FR-4.5

Recommendation Engine

  • Playbook matcher — maps the validated cause (or top hypothesis) to a vetted playbook via a rules-plus-embedding lookup against the Playbook Library.
  • Narrative generator — an LLM call constrained to the retrieved evidence set only, with a citation required per claim; an anti-hallucination guard rejects or flags any ungrounded sentence.
  • Synthesis & packaging — assembles Problem + Cause + Confidence + Action into the department report format.
  • Intelligent router — dispatches to the owning department's channel based on a segment-ownership mapping.
§4

End-to-End Data Flow

TRIGGER — scheduled sync or on-demand check fires for a monitored KPI.
INGEST — structured + unstructured sources write into the Observation Store.
DQ CHECK → STL → SIGNIFICANCE — noise is filtered; non-significant deviations are suppressed and logged.
SEGMENT → PARALLEL MINING — the confirmed anomaly is sliced and evidence is gathered from both structured and unstructured sources at once.
CONVERGENCE CHECK — validated cause, or routed to the Ambiguous Case Handler.
PLAYBOOK MATCH → NARRATIVE GENERATION — the cause is mapped to an action and phrased as a grounded report.
PACKAGE → ROUTE — the report is dispatched to the owning department's channel.

§7

Deployment Architecture

Each pipeline stage runs as a containerized service on Kubernetes and scales independently — Stage 2's statistical checks are cheap and frequent, Stage 3's evidence mining is heavier and bursty. A message queue (Kafka or SQS) decouples stages so a slow downstream service never blocks ingestion. Secrets and connector credentials are held in a vault service; structured logs and pipeline metrics feed an observability dashboard — the same discipline the product itself applies to its clients' KPIs.

§8

Security & Governance

  • Role-based access control on source connectors, the suppressed-log, and finished reports
  • Encryption in transit (TLS) and at rest for all stores
  • A PII-redaction pass on unstructured text before it enters the evidence index
  • Version-controlled playbooks and generation prompts, both with change history
  • Full evidence lineage retained per report — every claim resolves back to its source record
§9

Scalability & Failure Handling

  • KPIs are evaluated in parallel, partitioned by metric so one slow segment never delays another
  • The suppressed-log is capped and retention-windowed rather than growing unbounded
  • Each stage checkpoints its state so a retry resumes rather than restarts the pipeline
  • The convergence check fails closed: on any doubt, the system reports ambiguity rather than fabricating a single cause
§10

Future Enhancements

  • Feed analyst annotations back into playbook matching so the system improves with use
  • Move from scheduled to streaming anomaly detection for time-sensitive KPIs
  • Auto-draft new playbooks from recurring clusters of ambiguous cases
